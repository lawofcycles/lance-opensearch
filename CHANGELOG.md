# CHANGELOG

Inspired by [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Features

- The shard path fallback routes through the planner. A search body holding an element only the standard shard search path serves (`suggest`, `highlight`, `collapse`, `rescore`, a pipeline aggregation, `min_score`, `terminate_after`, `stored_fields`, `docvalue_fields`, `"explain": true`, `search_after` without a `sort`) translates to a shard path shape node naming each element as a reason, `PlanToShardPathRule` lowers it to the `ShardPathFallbackExec` operator of the shard path convention, and the dispatch filter forwards the request to the stock shard fan-out when that operator is the plan root. The hand written shape checklist in `LanceDispatchActionFilter` is gone; routing behaviour, response shapes and the explain endpoint's refusals are unchanged.
- The coordinator's fan-out and reduce run as plan operators. `FanOutExec` (the per-node request width and the fragment partitioning) and `MergeExec` (the reduce kind: aggregation reduce, hit page merge, count sum) join the Lucene convention, and a `PlanExecutor` traverses the coordinator's `MergeExec (FanOutExec (scan))` tree to drive the per-node transport fan-out and the merge of the gathered responses. On the fragment side the same executor resolves the planned query, sorted page, aggregation pushdown and matched-count routes the transport actions used to hand-roll. Runtime behaviour, response shapes and the explain output are unchanged.
- OpenSearch analyzer mode for text columns. `type: text_analyzer` joins the `overrides` clause on the attach body: attach adds a derived Utf8 column to the Lance table (`<column>__lance_tokens` unless `derived_column_name` names one), backfills it with the column's values run through the declared built-in OpenSearch `analyzer` (tokens joined by spaces, one AddColumns commit), and builds a whitespace inverted index with positions over it. The base column maps as `lance_text` with `tokens_column` and `meta.lance_analyzer`; `match`, `term`, `lance_match`, `lance_match_phrase`, `lance_multi_match`, `lance_fts_bool` and `lance_fts_boost` on it analyze the query text with the same analyzer and run against the derived column, so index-time and query-time tokenisation agree (an `english`-analyzed column matches `running` to `run`). `derive: async` on the attach body returns before the backfill and lets the namespace poll flip the mapping when the commit lands; the default `sync` blocks until the column is written and indexed. The existing `lance_text` path over Lance's native tokenizer is unchanged and remains the default for Utf8 columns that carry their own FTS index.
- The Lucene fallback joins the Volcano planner's cost comparison as its own convention: aggregation and hits trees the pushdown rules cannot fold into the Lance scan now plan as `LuceneAggregateExec` / `HeapTopKExec` physical operators over the bare scan instead of falling back to the logical plan, and `GET /<index>/_lance/explain` shows those operators as the physical root for such shapes. Trees that fold keep planning as the scan with pushed operations, preferred by a pinned cost. Search execution is unchanged.
- The hits page plans through Calcite: a request with a positive `size` translates to a hit shape over a top-k node over its query root, and the top-k pushdown rule folds the sort, the page size and the `search_after` cursor into the Lance scan whenever every sort clause resolves to a Lance column ordering. A `search_after` continuation of a sorted scalar page now runs as the same ordered, limited Lance scan with the cursor as a strict SQL bound ANDed into the scan filter (previously it collected through Lucene); a cursor equal to a missing-value sentinel, a sort mixing `_score` with a column, `_geo_distance`, script and nested sorts, and sorts over `ip` columns keep the Lucene collector. `GET /<index>/_lance/explain` now accepts hits requests (`size`, `sort`, `search_after`) and shows the fold.
- `type: geo_point` joins the `overrides` clause on the attach and namespace bodies. A Struct with two Float64 children named `(lat, lon)`, `(latitude, longitude)` or `(y, x)` in either order (the child names fix the storage order) and a FixedSizeList&lt;Float64&gt;[2] (with `overrides.<col>.order` selecting `lat_lon` or `lon_lat`) both map to OpenSearch's stock `geo_point` field type; every other Arrow shape is refused with 400 naming the column and its type. The fragment reader encodes each pair into the `LatLonDocValuesField` long layout and serves it as doc values (for `exists`, `_geo_distance` sort and the geo aggregations, which route through the shard path) and as a flat single-cell point tree (for `geo_distance` / `geo_bounding_box` / `geo_polygon` / `geo_shape`, whose stock queries need the points side of their `IndexOrDocValuesQuery`). No BKD splitting: a geo query visits every present row of a fragment, correct and proportional to fragment size. Predicates on the field never push down to Lance SQL; `_source` renders the point as a `{lat, lon}` object; Arrow-null and out-of-range rows are served as missing.
- Per-column Lance index type selection. The attach and namespace-register bodies accept an `indexes` clause (`{"<column>": {"scalar": "bitmap" | "zonemap" | "bloomfilter" | "btree" | "ngram" | "labellist" | "none", "vector": "ivf_flat" | "ivf_pq" | "ivf_sq" | "ivf_rq" | "ivf_hnsw_pq" | "ivf_hnsw_sq" | "none", "params": {...}}}`) selecting the type the build creates instead of the fixed BTree / IVF_PQ; `none` suppresses the automatic index on a column. `POST /_lance/build_indexes/{index}` accepts the same object as a one-shot, non-persisted override, its response's `built` entries carry the index type that was committed (`{"column": "tags", "type": "BITMAP"}`), and `GET /_lance/stats` reports the Lance index types present per column under `indices.<index>.index_types`. The preference persists inside `index.lance.overrides` and survives manifest version advances like the mapping overrides.
- `POST /_lance/namespace` accepts the catalog types `iceberg` (Iceberg REST catalogs), `polaris` (Apache Polaris generic tables) and `unity` (Unity Catalog) next to `directory`, `rest` and `glue`. The poll walks nested namespaces depth-first down to `config.max_namespace_depth` levels (default 2); `iceberg` and `polaris` root the walk at the required `config.warehouse`. Config values under the `credential` key name are now redacted like the other credential-bearing keys.
- `POST /_lance/namespace` accepts a catalog `type` (`directory` by default, `rest` for Lance Namespace REST catalogs, `glue` for the AWS Glue Data Catalog), a registration `name` that keys every namespace mutation, and a `config` object passed to the implementation's `initialize`. Config values under credential-bearing key names are redacted everywhere except the catalog initialisation itself; a catalog that fails to initialise or list shows `"status": "unavailable"` with its error in `GET /_lance/namespace` and is retried on every poll.
- Distributed search over Lance tables. Each Lance fragment is exposed as a Lucene leaf inside a shard, and full text and vector queries are rewritten to native Lance execution.
- `POST /_lance/namespace` registers a filesystem path as a Lance namespace and surfaces every `*.lance` table under it as an OpenSearch index. Uses `DirectoryNamespace` from `lance-namespace-core`.
- `POST /_lance/attach` attaches a single Lance table URI. Idempotent; a repeated call returns `already_attached: true`. Attach body accepts an optional `overrides` clause with per-column mapping rules (`type: date` on a signed integer column holding epoch millis, `type: keyword` on a Utf8 column with or without an inverted index, `format` with `type: date`, and keyword sub-fields via `fields`) — the legacy `multi_fields` clause still works as an alias that folds into `overrides.[col].fields` — a `"version": N` clause that pins a readonly snapshot, and a `storage_options` map for per-table object-store credentials. `POST /_lance/namespace` accepts the same `overrides` object and applies it to every table it surfaces that has the named columns.
- `POST /_lance/namespace/tables {"path": "..."}` previews the tables the poll would surface from a registered namespace. Returns 404 for unregistered paths so the caller can distinguish "not registered" from "registered but empty".
- `DELETE /_lance/namespace {"path": "..."}` stops polling a namespace. Already-surfaced indexes are left in place.
- `lance.namespace.poll_cadence` cluster setting controls how often each registered namespace is polled for new or advanced tables. Default 10s, minimum 1s.
- `lance.namespace.resurface_guard_grace` node setting (dynamic, default 1h) holds a deletion-tombstone for a Lance-backed index that was removed via `DELETE /{index}`, so the poll cycle honours the operator's intent for that window. Zero disables the guard.
- `index.lance.uncovered_fragment_policy` index setting (`wait` / `immediate`) controls the visibility of rows in fragments not yet covered by the current manifest.
- `index.lance.primary_key_field` index setting names the Lance column that answers `GET /<index>/_doc/<id>` lookups. `index.lance.primary_key_type` (`long`, `unsigned_long`, or `keyword`) carries the Arrow type family: signed integer PKs (up to 64 bits) resolve through `Long.parseLong`, UInt64 PKs resolve through `BigInteger` with a wide-decimal Lance filter and the column also surfaces as an `unsigned_long` mapping for term / range / sort / aggregation, and Utf8 PKs resolve through a SQL-quoted Lance filter with single-quote doubling for injection safety.
- `index.lance.overrides` index setting persists the per-column mapping overrides captured at attach or namespace-register time as canonical JSON, so the engine rehydrates them on shard open and the namespace poll reapplies them on manifest version advance (an override whose column disappears is kept and skipped until the column returns). The older `index.lance.multi_fields` setting stays registered and is read as a fallback so existing indexes keep resolving their keyword sub-fields; new attaches write only the new setting. Sub-field query resolution goes through Lucene doc values on the base column, no data duplication.
- Mapping derivation from the Lance Arrow schema for boolean, date/timestamp (all Arrow date/timestamp variants normalized to epoch millis), integer, `keyword` for Utf8 columns without an FTS index, `lance_text` for Utf8 columns with an FTS index, multi-valued `keyword` for list-of-Utf8, `knn_vector` for fixed-size-list-of-float, `binary` for Arrow binary and large binary columns, and a `fields` block per base column when the attach body carries a multi-fields declaration.
- Manifest version advance is picked up by a `ReferenceManager` swap under the read-only engine. No shard close, no reallocation.
- `lance_knn` DSL query issues one Lance nearest scan per shard and dispatches hits to the fragments they belong to. The coordinator merge reconstructs the global top-k.
- `GET /<index>/_doc/<id>` maps to `Dataset.newScan` with a `<field> = <literal>` filter restricted to the shard's fragments. Filter literal shape (integer or single-quoted string) is picked from `index.lance.primary_key_type`. A Lance scalar index answers in log time; without one, the same call falls back to a filtered scan.
- `_source` and `_id` come from stored fields synthesised on the fly from the Lance row. Tables without a declared primary key still emit unique `_id` values through a `<fragment>-<offset>` fallback so sort-by-`_id` and `_mget` dedup stay correct.
- Auto-build of missing FTS / scalar / vector indexes for tables at or under `lance.builder.max_rows` rows (default 1,000,000). `POST /_lance/build_indexes/{index}` triggers manual builds with optional `columns` and `fragment_ids` for larger tables or incremental builds.
- Fragment path is the single search implementation. Coordinator response envelope tracks per-hit scores (Lucene's 4 / 5 argument `search` / `searchAfter` overloads) so `sort` combined with `track_scores: true` preserves `_score`, and `max_score` reports the largest per-hit score in the paged window. Attach and namespace surface persist all metadata the fragment path and engine path need on shard open.
- Aggregation pushdown: a `size: 0` request over `match_all` or a scalar filter whose aggregations are metrics only, or one `terms` / `histogram` / fixed interval `date_histogram` with metric children, runs as a Substrait `AggregateRel` inside the Lance scan (one row per group per executor; the coordinator reduce is unchanged; `hits.total` from the same scan). `lance.aggregation.pushdown` (dynamic, default `true`) turns it off.
- Aggregation pushdown runs each executor's fragments in up to `lance.aggregation.pushdown_parallelism` scans at once (dynamic, default half the CPUs, 1 to 32) and merges the group rows before building buckets; `date_histogram` with a `calendar_interval` (`second` to `year`, UTC, no offset) on a timestamp column joins the pushdown through DataFusion's `date_trunc`.
- Heap column loads (a column the off-heap column store has no room for, or every column when the cache is off) are charged to the request circuit breaker before allocation and given back when the reader closes. A load the breaker refuses ends the request with HTTP 429 `circuit_breaking_exception` naming the column and the bytes it asked for instead of taking the node down with `OutOfMemoryError`. `GET /_lance/stats` reports `column_store.heap_fallback_bytes` and `column_store.heap_fallback_rejections`.
- Aggregation pushdown for nested buckets and `composite`: a chain of up to three `terms` / `histogram` / `date_histogram` (fixed or calendar interval) levels with metric children at every level, and `composite` over `terms` / fixed length `date_histogram` sources with `size` and `after` paging, run as one group by over every key. `lance.aggregation.pushdown_max_groups` (node setting, default 1,000,000) bounds the estimated key combinations (the product of the `terms` levels' `shard_size`) above which a tree takes the aggregators. `composite` over `terms` / `date_histogram` sources also joins the fragment path allow list.
- Aggregation pushdown for the rest of the allow list: `stats` / `extended_stats` as scan measures; `range` / `date_range` / `filter` / `filters` / `missing` as bucket levels (the scan groups by the bit set of the ranges or filters a row falls in, so overlapping ranges and filters count a row in each, and every bucket is reported); `cardinality` from a `group by` on the field whose distinct values the executor hashes into the HyperLogLog++ sketch as it reads them; tdigest `percentiles` / `percentile_ranks` from a second scan that counts the rows of `lance.aggregation.percentiles_bins` equal width bins (dynamic, default 4096) between the field's minimum and maximum, each bin's rows fed to the TDigest at the bin's edges and centre, so the histogram the digest sees is accurate to one bin width. `filter` / `filters` queries are translated to Substrait predicates with the Lucene semantics (`must_not` keeps rows without a value, `should` is optional next to `must` / `filter`).
- `lance_coordinator` thread pool (`thread_pool.lance_coordinator.size`, default `max(1, allocated processors / 2)`; `thread_pool.lance_coordinator.queue_size`, default 10,000) runs the coordinator half of every fragment path request: the entry and the merge of the per-node answers. Fragment responses are received on the transport thread and only stored there, so the transport layer never queues one on a bounded pool. A full pool fails the request with HTTP 429 (`rejected_execution_exception` naming the pool) instead of running it on the shard path.
- The request's `timeout` (else `search.default_search_timeout`) bounds every per-node fragment request. A node that does not answer in time has its executor task cancelled and the request answers from the other nodes with `timed_out: true` and `hits.total` as `gte`, or fails with HTTP 504 under `allow_partial_search_results: false`. The executors run as cancellable child tasks of the coordinator task, itself a child of the search task, so `_tasks/_cancel` on the search and a client that disconnects stop the Lance scans at their next batch boundary instead of leaving them to run to the end.
- `wildcard`, `regexp` and `prefix` on a `lance_text` column (previously 400) run as a Lance scan filter over the stored string (`LIKE` / `ILIKE` with a backslash escape, `regexp_like` over the anchored pattern in Rust regex syntax, `starts_with`), with `case_insensitive` honoured; the same three queries on a `keyword` column, inside `bool`, in `lance_knn.filter` and as an FTS prefilter take the same SQL, and `_count` / `size: 0` use the count only scan. Lucene only regexp operators (`~`, `&`, `<n-m>`, `@`, `#`, `"..."`) answer 400.
- The fragment path allow list accepts `stats`, `extended_stats`, `percentiles`, `percentile_ranks`, `cardinality`, `range`, `date_range`, `missing`, `composite` (terms / histogram / date_histogram sources over a field) and `filter` / `filters` over scalar queries, so requests with those aggregations fan out to every data node instead of reading the whole table on one node through the shard path. Scripts, pipelines and the other types still take the shard path.
- Column loads of a fragment path request (the off-heap store's and the heap fallback's) scan the node's fragments in up to `lance.fragment_path.parallelism` contiguous groups side by side on the `search` pool (dynamic, default half the CPUs, 1 to 32), so a column is read into its arrays on several cores instead of one.
- A fragment path executor collects its hits and aggregations in up to `lance.fragment_path.slices` slices (dynamic, default half the CPUs, 1 to 32) on the `search` pool, one collector or aggregator tree per slice, and reduces the slice results before answering, the way concurrent segment search collects a shard's segments. `1` collects on the request's thread alone as before.
- Index warm-up: when a Lance-backed index appears in the cluster state (attach, namespace poll, node restart), every data node reads the table's indexes into its Lance Session cache in the background on the new single threaded `lance_warm_up` pool, so the first request does not load them on its own thread. `lance.attach.warm_indexes` (node setting, dynamic, default `metadata`) selects `none`, `metadata` (open every index: BTree page lookup, bitmap keys, full-text token dictionaries, IVF centroids and one partition) or `all` (every BTree page, bitmap and IVF partition as well, unless the table's index files exceed half the index cache). `GET /_lance/stats` reports the warm-ups in a `warm_up` block per node.
- Tables with more rows than one Lucene reader may hold (`IndexWriter.MAX_DOCS`, 2,147,483,519) are searchable: the coordinator sends one fragment request per group of a node's fragments that fits the bound and merges the groups' responses like nodes', the shard reader holds the leading fragments that fit so the index is green, GET reaches every row through the Lance scan, attach answers `lucene_bound_exceeded: true` and logs a WARN, `GET /_lance/stats` reports `indices.<index>.rows` / `shard_reader_rows` / `lucene_bound_exceeded` per hosted shard, and a request shape only the shard path serves is refused with 400 against such a table instead of answering from part of it. `lance.test.max_docs_per_reader` (node scope, dynamic) lowers the bound for tests.
- Aggregation pushdown reads Lance's group rows into primitive columns (encoded keys, a byte dictionary for strings, parallel count and measure arrays behind an open-addressing group table) instead of allocating boxed keys and per metric state objects per row, so the Java side of a high cardinality `terms` no longer outweighs Lance's aggregation. A single `terms` level ordered by `_count` or by one of its own single value metric children (now also a pushdown shape) keeps only the best `shard_size * lance.aggregation.pushdown_topk_slack` groups per scan (new dynamic node setting, default 4, 1 to 64); the counts a key earned in different scans are summed before the final `shard_size` cut, everything else stays counted in `sum_other_doc_count`, and `doc_count_error_upper_bound` keeps its cross shard meaning. `_key` ordered single level `terms` sort and cut in the primitive columns and box only the returned buckets.
- The Substrait producer can put a `SortRel` and a `FetchRel` above the aggregate (`SubstraitAggregatePlan.Builder#topK`). Nothing sends it: Lance 12's consumer accepts an `AggregateRel` root only, so the executor keeps cutting top-k in Java until a Lance release takes the sorted cut.
- `index.lance.index_placement` index setting (`in_table` / `node_local`, attach body key `index_placement`) supports tables on sources the OpenSearch process cannot write to: with `node_local`, every data node shallow-clones the table into `<data path>/lance-local/<index name>/` (`Dataset.shallowClone`, metadata only), `POST /_lance/build_indexes/{index}` fans out so each node builds FTS / scalar / vector indexes into its own clone (per-node outcomes under `nodes` in the response), reads on the node open the clone, deleting the index removes the clones, and `GET /_lance/stats` reports each clone under `local_clones` with `local_clone_bytes` and `source_version`. The source table is never written.
- Arrow `Struct` columns surface as `object` fields with `properties` derived from the struct's children, recursing into nested structs. Term / terms / range / exists queries, sort, and aggregations resolve on the `parent.child` path through per-child doc values, filters on struct children push down to Lance SQL as nested field accesses, `_source` and GET by id render the struct as a nested JSON object (a null child renders as JSON `null`), and an unsupported child type is skipped with a note while the parent object is still emitted. FTS and knn on struct children are not derived.
- `GET /{index}/_lance/explain` (preview) returns the logical plan the Calcite based planner builds for a search body, as `{"index": ..., "logical": "...", "physical": "..."}`. Supported today: a `size: 0` request with every aggregation tree the pushdown computes, metric only trees (`sum`, `avg`, `min`, `max`, `value_count`, `stats`, `extended_stats`, `cardinality`, tdigest `percentiles` / `percentile_ranks`), a chain of up to three bucket levels (`terms`, `histogram`, `date_histogram`, `range`, `date_range`, `filter`, `filters`, `missing`) with metric children, and `composite` over `terms` / fixed length `date_histogram` sources, planned as a `LanceAggregate` node that prints the bucket and metric options; anything else answers 400 naming the first unsupported element. The `query` clause plans as a filter over the scan (`term`, `terms`, `range`, `exists`, `bool`, `wildcard`, `regexp`, `prefix`, `ids`, `match_none`). The `physical` section shows the Volcano planner's output: the `LanceTableScan` carrying the pushed aggregate when the Substrait producer accepted the shape, and the pushed filter when the planner can spell the predicate in Lance SQL. The endpoint only reports; no request executes through the planner and the plan text format will change.
- Arrow `List<Struct>` columns surface as `nested` fields. Each list element becomes a hidden child document placed before its row's parent document, so `nested` queries with `term` / `range` / `exists` / `bool` inner queries match several attributes of the same element, alone or combined with top-level clauses; `hits.total`, `_count` and `match_all` count parents only, `_source` and GET render the array of element objects, `GET /_lance/stats` reports the child docs as `nested_docs`, and the attach-time Lucene bound counts rows plus nested elements. `inner_hits` is refused with 400, the `nested` aggregation stays on the shard path allow list exclusion, and nested predicates are not pushed to Lance SQL.
- `type: ip` joins the `overrides` clause on the attach and namespace bodies: a Utf8 (or `List<Utf8>`) column of IP address strings maps as `ip`, the fragment reader parses each string and serves the 16 byte `InetAddressPoint` encoding through doc values, so `term` (exact or CIDR notation), `terms`, `range`, `exists`, sort and `terms` aggregations behave as on a stock `ip` field with address order rather than string order. Strings that do not parse are served as missing (logged once per fragment with a count) while staying readable in `_source`; a keyword sub-field on the ip column serves the raw strings for exact string match. Predicates on an ip field never push down to Lance SQL and are evaluated by Lucene over the encoded doc values.
- `type: wildcard` joins the `overrides` clause on a Utf8 column: the operator's intent is recorded in `meta.lance_override_type` while the column is served by the keyword doc values path (`wildcard`, `prefix`, `regexp` and `term` against SortedSetDocValues, with the existing Lance SQL pushdown of those patterns), because the n gram accelerated `wildcard` field type of OpenSearch core needs postings the fragment reader does not have.
- A Lance column rename (same immutable field id, new name) carries the operator's mapping state across: the namespace poll re-keys every `index.lance.overrides` entry (the per-column overrides and the `indexes` clause's index preferences alike) from the old column name to the new one before re-deriving the mapping, so `type` / `format` / `fields` rules follow the column; `index.lance.overrides` is now dynamic because the poll itself rewrites it. On a schema reset (a column cast to a new type) an override the new type still admits stays in the setting, one it does not admit is dropped with a warning naming the column, the override and the new type. The stale name the mapping keeps (marked `meta.lance_dropped`) is hidden from the read paths: scalar queries against it answer 0 hits instead of reaching Lance SQL, `GET /{index}/_lance/explain` refuses an aggregation on it naming the rename, and `GET /_lance/stats` reports every recorded rename under `indices.<index>.renamed_fields` as `{"from", "to", "lance_field_id"}` entries.
- Full-text and knn queries plan through the Calcite planner. A top-level Lance FTS clause (`lance_match`, `lance_match_phrase`, `lance_multi_match`, `lance_fts_bool`, `lance_fts_boost`, alone or as the single `must` of a `bool` with scalar `filter` / `must_not` companions) and a top-level `lance_knn` (optionally with its inner `filter`) translate to `LanceFtsMatch` / `LanceKnnSearch` plan nodes; fuse rules fold them into the `LanceTableScan` as pushed `fts` / `knn` operations whose filter SQL the scan evaluates as a Lance prefilter, and `GET /{index}/_lance/explain` shows both. The scalar filter SQL of every fragment request is derived by the same translator and printer, replacing the string-building translator (`LanceKnnFilterTranslator` is deleted); date range bounds now honour the query's `format` / `time_zone`, `must_not` keeps rows without a value and `should` next to `must` / `filter` is optional, as on a Lucene index, and predicates on `ip` override columns stay on the Lucene side.

### Changed

- `index.lance.tag` is now a dynamic index setting. Operators can repoint the tag on a running index with `PUT /{index}/_settings` and the next namespace poll refreshes the reader onto the version the new tag points at (empty reverts to latest-follow), so detach and reattach are no longer needed to move an index between tags.
- `LanceTableScan.withPushedFilter` and `withPushedAggregate` refuse a scan already carrying any other pushed operation, matching `withPushedFts` and `withPushedKnn`. The rule side already enforces the "at most one query kind, optionally combined with a top-k" invariant through bare scan operand predicates; the scan API side used to accept a filter or aggregate on top of a scan another rule had pushed. The `PushedOperation` sealed interface javadoc now states the mutual exclusion invariant so any new permit implementor sees it.

### Fixed

- `cardinality` aggregations run through the aggregator path by default: the planner's pushdown rule no longer folds a tree carrying one into the Lance scan, because the pushed implementation (feeding the field's distinct values into the HyperLogLog++ sketch one by one) is 3.6x to 46x slower than the aggregators on large tables. The cardinality result is identical. (#208)
- The full-text admission gate reads the kernel's `MemAvailable` (from `/proc/meminfo`) instead of `MemFree`, matching the memory the kernel would actually hand to the scan: `MemFree` excludes the reclaimable page cache and slab, so on a node whose page cache was warm from serving queries the gate saw close to zero and refused unbounded full-text shapes the node could serve (429 `lance_fts_admission` with `[0b] available after [8gb] headroom`). Where `/proc/meminfo` or the line does not exist (macOS, Windows) the gate falls back to the free physical memory as before. `GET /_lance/stats` now reports the reading as `fts.admission.available_bytes`.
- The collection slices, the column load group scans and the aggregation pushdown scans of a fragment path request are submitted to the node's `index_searcher` pool (the pool concurrent segment search uses) instead of the SEARCH pool the request itself executes on. A task submitted to the SEARCH pool stays in its bounded queue as a spent entry after the request's thread has run it, and with every SEARCH thread parked at the fragment path admission semaphore those entries drain only when a request completes, so each waiting fragment request trapped the tasks of the requests executing behind it and the queue population multiplied with the client fan-in: a 6 node cluster serving a 100M row table answered 72 % of 256 concurrent mixed requests with 429 (`search` pool rejections) while the same mix at 64 passed. On the `index_searcher` pool the intra request work has its own queue, and a full or rejecting pool degrades a request to its own thread instead of failing it.
- `storage_options` values of registered namespaces follow the same redaction rule as `config`: in the cluster state API (`GET _cluster/state/metadata`, custom `lance.namespaces`) and in log lines, values whose key contains `secret`, `password`, `token`, `key`, `authorization` or `credential` render as `***`. Only the gateway-persisted state keeps the raw values so a full cluster restart reopens the tables with working credentials. Previously the raw object store credentials passed at registration were readable by any caller with `cluster:monitor/state`.
- A plain sorted page (`sort` without aggregations) on a dotted field name no longer answers 400. The sort pushdown's column resolution used Arrow's `Schema.findField`, which throws for any non-top-level name instead of returning null, so a sort on a multi-field sub-field (`body.raw`) never reached its base-column fallback and a sort on a struct child (`meta.score`) could not fall back to the Lucene collector.

- The Lance scan behind a full-text or knn query returns `_rowaddr` and `_score` (`_distance` for knn) only. Without a projection Lance materialised every column of every matching row into the Arrow batches, so an unbounded full-text shape (sort by a field, aggregation, `size 0`) over a large match set held native memory proportional to matches times row width and the kernel killed the node, and past 2 GiB of text in one take the Utf8 offsets overflowed into a 500.
- The hit buffers a full-text or knn query keeps on heap are reserved with the `request` circuit breaker (label `lance_fts_hits`) before they are allocated and returned when the request ends, so a hit set the heap cannot hold answers 429 `circuit_breaking_exception` instead of `OutOfMemoryError`.
- `hits.total` with a bounded `track_total_hits` reports the bound as the value whenever the relation is `gte`, as the shard path does. On several data nodes each executor counts its own fragments' share of one scan stopped at the bound, and Lance returns different tied rows to each of them, so the shares could add up to less than the bound and the response read, for example, `{"value": 9991, "relation": "gte"}` under the default bound of 10,000.
- Unbounded full-text shapes (sort by a field, aggregations, `size 0`, `_count`, `track_total_hits: true`) over an inverted index that does not fit the index cache shard are refused with 429 `circuit_breaking_exception` (label `lance_fts_admission`) before the scan starts when the node's free physical memory minus `lance.fts.admission.headroom` (dynamic, default `8gb`) cannot hold the estimated native rebuild of the index's document set (`rows × 52 bytes`). That rebuild is allocated by Lance outside the JVM and outside every budget the plugin accounts, so on a large enough table the scan ended the node with a kernel OOM kill that no breaker could see. `lance.fts.admission.enabled` (dynamic, default `true`) turns the gate off; bounded top-k pages are not gated. `GET /_lance/stats` reports `fts.admission.enabled`, `headroom_bytes`, `rejections` and `last_estimate_bytes` per node.
- The count of a scalar filter (`term`, `range`, `bool` of those) no longer pulls every matching row through JNI on one search thread. With `track_total_hits: true` (and `_count`) the executor asks Lance to count natively over its fragments and receives one number; under an integer bound (default 10,000) the count scan stops at `bound + 1` rows and reports a lower bound instead of counting every match. A `term` matching a quarter of a billion rows took 15 to 20 s of a single core for a `size 0` or `size 10` request; the native count for the same filter takes the time of Lance's own `count_rows`.

### Maintenance

- The per-fragment leaf reader builds its cache lifetime bridge (a one-doc in-heap Lucene index that supplies `IndexReader.CacheKey`) on the first cache helper request instead of in the constructor, so a fragment path request over many fragments no longer pays one `IndexWriter` commit per leaf when nothing on its path asks for a leaf-level cache key.
- Upgrade `org.lance:lance-core` to `12.0.0` (from `11.0.0`), `org.lance:lance-namespace-core` and `org.lance:lance-namespace-apache-client` to `0.11.1` (from `0.7.7`), and Arrow to `18.3.0` (from `18.1.0`).
