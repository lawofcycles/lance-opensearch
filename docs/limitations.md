# Known limitations

Everything documented here is a shape the plugin refuses, a shape that answers differently from an ordinary index, a workaround, or something deferred to a future ticket. Grouped by concern.

## Search body elements the plugin refuses

Every `_search` over a Lance backed target runs on the fragment executors. A body carrying an element no plan answers is refused with 400 `illegal_argument_exception` naming the element, at the coordinator before a table is opened, and `GET /_plugins/_lance/explain/{index}` reports the same body as `route: unsupported` with the same message under `unplanned`. The elements and their messages:

- `suggest`: refused, ``search body carries a `suggest` clause which needs full-text APIs Lance does not surface. See `docs/limitations.md`.`` The term, phrase and completion suggesters read candidate terms from an inverted index, which the fragment leaves do not carry and Lance's full text index does not expose through the Java SDK.
- `highlight`: refused, ``search body carries a `highlight` clause which needs full-text APIs Lance does not surface.`` Highlighting needs term positions in the stored text, which the Lance Java SDK does not expose. A body carrying both elements is refused for its `suggest`.
- `inner_hits` on a `nested` query: refused, `[inner_hits] on the nested query [path=...] is not supported for Lance-backed indices`, by the dispatch filter before the coordinator runs, since neither the fragment executor nor the shard engine materialises the block. `inner_hits` under `collapse` is served ([features.md](features.md#query-shapes)).

A request Lance refuses as invalid input (for example `lance_match_phrase` on an FTS index built without positions) answers 400 `illegal_argument_exception` with Lance's message; [design/lance-error-mapping.md](design/lance-error-mapping.md) records how Lance's exceptions map onto the status.

## Search pipelines

A search pipeline (`search_pipeline` parameter or `index.search.default_pipeline`) is not applied to a search whose targets are all Lance backed: the fragment path takes the request before `TransportSearchAction` resolves the pipeline, and no request, response or phase results processor runs ([features.md](features.md#hybrid-search), issue #422). A search that mixes a Lance backed index with an ordinary one stays on the stock search action and runs its pipeline as usual. Search templates are rendered before dispatch and are not affected.

## Query types the field types refuse

Refused with 400 on both paths, by the field types themselves, with the same message on OpenSearch's stock search action over the whole table reader. The fragment leaves carry doc values, the Lance full text and vector indexes, and the parent join of nested columns, but no postings, positions, term statistics or points ([features.md](features.md#query-dsl-matrix) lists every query type and what evaluates it), and these query types read what the leaves do not carry:

- `intervals`: `Can only use interval queries on text fields - not on [body] which is of type [lance_text]`.
- `match_phrase_prefix`: `Can only use phrase prefix queries on text fields - not on [body] which is of type [lance_text]`.
- `span_term`, `span_near`, `span_first` and the other `span_*` queries: `Cannot extract a term from a query of type class org.opensearch.lance.query.LanceFtsQuery: ...`; the span builders extract a Lucene term from the field type's term query, and the Lance full text query is not a term query.
- `more_like_this`: `more_like_this only supports text/keyword fields: [body]`.
- `has_child`, `has_parent`, `parent_id`: `[has_child] no join field has been configured`; no join field is derived from a Lance table.

Lance's inverted index exposes neither positions nor term statistics through the Java SDK; span, interval and more like this queries wait on that API.

## `ids` outside the translator

`ids` inside a shape the translator refuses matches nothing, and `ids` on a table without a primary key matches nothing. Elsewhere `ids` translates to a predicate on the primary key column and is served by the Lance scan under every envelope.

- The `_id` field itself has no postings on the fragment leaves: the id is synthesised from the key column, or from the row address on a table without a primary key. Inside a shape the translator refuses (a `bool` with `minimum_should_match`, a `function_score` with a `script_score` function, a `nested` query) the clause is built by the Lucene composition as a terms query on `_id` and matches nothing.
- A table without a primary key has no `ids` translation at all, and the query matches nothing there.
- The same holds for OpenSearch's stock search action over the whole table reader.

## Score shaping queries on a scored request

`constant_score`, `dis_max`, `boosting` and `function_score`, and a `bool` whose optional `should` clauses would score its matches apart, are served by the Lucene composition on a scored request. They translate to a predicate only where no score is read (a count, an aggregation request, a page ordered by stored columns).

- The predicate scores every row `1.0`, so on a page in score order, with `track_scores`, `min_score`, `rescore` or `collapse` those queries take the Lucene composition, which orders the page the way the query asks. The count and the aggregations of the same request are then Lucene's as well, not a Lance count scan or a pushed aggregate.
- `GET /_plugins/_lance/explain/<index>` reports the choice under `unplanned` (`query type [dis_max] on a scored request`, `bool with optional should clauses on a scored request`).
- A `bool` whose every clause scores every match alike (`must` and `filter` clauses only, or a single `should`) translates under every envelope. Its Lucene score would be the sum of its clauses' scores where the pushed page reports `1.0`, and `track_scores` over a pushed page reports `1.0` for every hit.

## Aggregation answers that differ from a single reader

- `percentiles` with the default tdigest method and `cardinality` are served, approximate: one sketch per executor, merged by the coordinator the way OpenSearch merges them across shards. The merged value is within the sketch's error of the value a single reader over the whole table computes, not identical to it, and can move when the fragment to node assignment changes.
  - Inside an executor the sketch is built per collection slice and the slices are merged as well, so the value also moves with `plugins.lance.fragment_path.slices`. Set it to `1` for one sketch per executor.
  - When the aggregation pushdown answers a tdigest `percentiles` / `percentile_ranks` ([aggregations.md](aggregations.md#percentiles)), the executor's sketch is fed from what Lance aggregated rather than from every document: the tdigest receives each of `plugins.lance.aggregation.percentiles_bins` equal width bins over the field's `[min, max]` as one value at each bin edge and the rest at the centre.
  - The histogram is accurate to the bin width (`(max - min) / bins`, 0.025 % of the range at the default 4096), and the digest built from those few thousand weighted points interpolates less accurately than one built from every document (measured at 0.16 % of the range for a p95 over a long tailed field of 20M rows).
  - `cardinality` is a cost decision, not a rule: the planner enumerates the pushed form of any tree carrying one and prices it against the aggregator, and with the current coefficients the aggregator side wins on every measured table, because the pushed form hashes every row into the sketch and then feeds the distinct values into it one by one on a single thread. A change of the coefficients, not a rule, would move the choice. Both forms return the same count.
    - Measured: `cardinality(user_id)`, 10M distinct values, 22.6 s pushed against 4.0 s on four nodes at 1B rows; `cardinality(category)`, 200 distinct values, 71 ms against 35 ms on one node at 20M rows.
  - `hdr` percentiles, `stats`, `extended_stats`, `range`, `date_range`, `missing`, `filter`, `filters` and `composite` are exact at every node and slice count.
- A `terms` aggregation whose `shard_size` is below the number of distinct values is served, differs from a single reader in its buckets: it reports a `doc_count_error_upper_bound` above zero and may keep other buckets when `plugins.lance.fragment_path.slices` is above 1. Every slice cuts its own share of the buckets to `shard_size` and the executor's reduce merges what the slices kept, which is what a shard does with concurrent segment search on. With `slices: 1`, and with the aggregation pushdown, the cut happens once per executor and the error is zero.

## Mixed targets

A search whose target expands to several indexes is served, and routes by the backing of every target.

- When every index is Lance backed the coordinator fans out once per index and merges the pages, sums the totals and reduces the indexes' aggregation trees together, as OpenSearch reduces the shards of several indexes. A field mapped to different types in two of the indexes fails the reduce with OpenSearch's error.
- When one target is not Lance backed (an ordinary index, or an alias to one) the whole request runs on OpenSearch's stock search action, which reads the Lance index through the shard engine's whole table reader and answers over every index with its own wire shape (`_shards` counts one shard per index). That is the one `_search` route left that reads the shard reader, and it differs from the fragment path in three ways.
  - Against a table above the Lucene document bound ([features.md](features.md#tables-above-the-lucene-document-bound)) the reader holds the leading fragments that fit, so the request answers from part of the table without saying so.
  - A body with `suggest` or `highlight` is not refused there, and OpenSearch's own suggest and highlight phases run over a reader whose leaves carry no postings, so what they return for a Lance field is not something the plugin supports.
  - A request Lance refuses as invalid input answers 500 instead of 400, because Lucene's query phase wraps the failure in `QueryPhaseExecutionException`, which OpenSearch reports as a server error, and the plugin does not intercept that phase. Lance's message is still in the response body.
- `GET /_plugins/_lance/explain/{index}` does not reflect the mixed target check: it explains the index alone, with the fragment plan the body has there.

## Aggregations the fragment path does not serve

Every aggregation type goes to the fragment path; the coordinator's translator refuses the request with 400 `illegal_argument_exception` (`aggregation type [global] on [g] is not supported for Lance-backed indices: ...`) when the tree holds one of the following, wherever it sits and whatever the query or page. The explain endpoint answers the same 400.

- `global`: refused. OpenSearch's aggregation phase collects it in a pass of its own over every document of the index (`AggregationPhase` runs the global aggregators under a match all query); the fragment executor collects one pass under the request's query, so the bucket would hold the filtered count. Candidate for a second collection pass on the executor.
- `top_hits`: refused. It builds its hits through the search context's fetch phase, which the fragment executor's context does not carry (the executor's own hits go through a separate fetch). Candidate once the executor's fetch is reachable from an aggregator.
- `rare_terms`: refused. Its aggregator seeds itself from `indexShard().shardId()`, and the fragment executor runs without a shard.
- `significant_terms` and `significant_text`: refused. They score terms against background frequencies from the inverted index, which Lance leaves do not carry; the stock factory refuses every Lance derived field as not searchable on an ordinary shard as well.

Served with a difference from a single shard:

- `variable_width_histogram` is served, approximate, as it is across the shards of an ordinary index: each executor clusters the values in the order its collection sees them and the coordinator merges the clusters, so a bucket's bounds and count can differ from a single shard's clustering by a few rows at the cluster boundaries.
- `sampler` and `diversified_sampler` are served, with the sample taken per collection slice per executor: each slice keeps `shard_size` documents, as each slice does under concurrent segment search on a shard, so a request over three executors with `plugins.lance.fragment_path.slices` 2 samples up to six times `shard_size` documents. Set `plugins.lance.fragment_path.slices` to `1` for `shard_size` per executor.
- A `filter` / `filters` bucket over a Lance full text or `lance_knn` clause runs one Lance scan per bucket on every executor for its `Weight`, outside the request's own scan, as the same bucket does over the shard engine's whole table reader.

## Aggregation shapes the scan does not compute

The Substrait aggregation pushdown ([aggregations.md](aggregations.md)) covers metric only trees, a chain of up to three bucket levels with metric children, and `composite` over `terms` / `date_histogram` sources. Everything else runs through the Lucene aggregators over the fragment readers, which walk every document of the aggregated column:

- Bucket trees deeper than three levels, two bucket aggregations under the same parent, a bucket under a `composite`, or a nested tree whose estimated key combinations exceed `plugins.lance.aggregation.pushdown_max_groups`, as the planner estimates them from the table statistics or as the executor estimates them from the request shape (the product of the `terms` levels' `shard_size` and the `range` / `filters` levels' bucket count plus one).
- `composite` with `missing_bucket: true`, a `histogram` or `geotile_grid` source, a script source, or a `date_histogram` source with a `calendar_interval` of a month or longer, a `time_zone` or an `offset`.
- `hdr` percentiles and `percentile_ranks` (the sketch has no merge from binned counts); `cardinality` (the pushed form, which hashes every row and then feeds the field's distinct values into the sketch one by one, is priced above the aggregator on every measured table, so the cost comparison sends the tree to the aggregators; no rule refuses it); `range` / `date_range` / `filters` with more than 62 ranges or filters; `range` on a `keyword` or `boolean` field, `date_range` on a field that is not a `date`.
- A `filter` / `filters` whose query the pushdown cannot spell as a predicate: `wildcard`, `regexp` and `prefix` (served by the aggregators through Lucene, not translated to a Substrait predicate), a `match` or any other query type, a Lance full text or `lance_knn` clause, a `bool` with `minimum_should_match`, a `range` on a `keyword` or `boolean`, a `term` on a `text` or `lance_text` field or on a `list<utf8>` column, a fractional value against an integer field, an unmapped field.
- `terms` ordered by `_count` ascending or by a sub-aggregation, `min_doc_count` other than 1, `include` / `exclude`, `missing`; `terms` on a `list<utf8>` column (a group by on the list counts rows, not elements).
- `histogram` with `offset`, `extended_bounds` or `hard_bounds`, or on a `date` / `boolean` field; `date_histogram` with `offset`, `time_zone` or bounds; `date_histogram` with `calendar_interval` on a `date32` / `date64` column or on a timestamp column whose Arrow zone is not UTC (DataFusion's `date_trunc` takes a timestamp array and truncates on the column's zone).
- Metrics with a script, `missing` or `value_type`; `sum` / `avg` / `min` / `max` / `stats` / `extended_stats` / `percentiles` on a `keyword`.
- Any aggregation over a full-text or `lance_knn` query, with a `post_filter`, with hits, or under a reader wrapper (security plugin DLS / FLS).
- A `meta` object that is present but empty is not echoed by the pushdown (the builder exposes an empty map for both cases).
- `sum` and `avg` on `float` / `double` columns add the values in the scan's order without the aggregators' compensated summation, so the last bits of a floating point sum can differ between the two paths.

## FTS query behaviour on stock `match` / `match_phrase` / `multi_match`

OpenSearch's stock `match`, `match_phrase` and `multi_match` (type `best_fields`) on a `lance_text` field are rewritten by the coordinator into `lance_match`, `lance_match_phrase` and `lance_multi_match` with the same parameters, so `operator`, `fuzziness`, `prefix_length`, `max_expansions`, phrase order, `slop` and per field boosts reach Lance. What does not:

- `minimum_should_match`, `zero_terms_query`, `lenient`, `fuzzy_transpositions`, `fuzzy_rewrite`, `auto_generate_synonyms_phrase_query` are ignored: the whole query text is one Lance query and Lance's Java SDK exposes no equivalent knob.
- `fuzziness: AUTO` resolves to one edit distance for the whole query text (0 under three characters, 1 under six, else 2), where Lucene would derive it per term.
- `multi_match` of type `most_fields`, `cross_fields`, `phrase`, `phrase_prefix` or `bool_prefix`, with `fuzziness` or a non default `tie_breaker`, or naming a field pattern or a field that is not `lance_text`, keeps its stock form: one Lance match per field, combined by Lucene.
- A clause with an explicit `analyzer` keeps its stock form: OpenSearch tokenises the text and Lucene combines one Lance match per token.
- Inside a compound the rewrite does not descend into (`function_score`, `nested`, `constant_score`, `boosting`; it descends into `bool` and `dis_max`) the field type answers the stock clause itself: `match` runs the whole text as one Lance match and its `operator` is not applied, `match_phrase` of two or more words runs as a Lance phrase with its `slop`, a one word `match_phrase` runs as a Lance match.
- `match_phrase_prefix`, `query_string`, `simple_query_string`, `intervals` and the `span_*` queries are not rewritten.

A `match` on a column declared `lance_text` without an inverted index ([mapping-overrides.md](mapping-overrides.md#type-lance_text)) makes Lance read and tokenise every row of the scanned fragments on each request, so its time grows with the row count where an indexed column's does not.

The admission gate bounds the memory of that scan ([admission.md](admission.md#fts_flat)) and not its time. Set `search.default_search_timeout` on a cluster that serves Lance tables, or a `timeout` on the request: the plugin honours both and returns the partial answer in time, but the cancelled flat scan runs to its end on the executor, so the timeout bounds the client's wait and not the executor's CPU or native memory ([Shard model and concurrency](#shard-model-and-concurrency)). The plugin adds no timeout setting of its own.

When the security plugin's field level security hides a `lance_text` column from the caller, `match`, `lance_match`, `lance_match_phrase` and `lance_multi_match` on that column answer 0 hits: the full text query checks the column against the wrapped reader's `FieldInfos` on every leaf and contributes nothing where the column is absent.

`term` on the same hidden column answers the count of matching rows, as it does under field level security on a stock index, because the planner runs it as a Lance scan filter over the column's stored values and not through the inverted index. A caller who may not see the column can therefore still learn how many rows carry a given exact value through `term`; `terms` and `exists` take the same scan filter path and are expected to behave the same, not yet measured under field level security.

## regexp on `lance_text`

`regexp` on a `lance_text` (or `keyword`) column is served with Rust regex syntax and semantics, not Lucene's `RegExp` grammar: DataFusion's `regexp_like`, that is the Rust `regex` crate, evaluates the pattern over the stored string. The plugin anchors the pattern (`^(?:...)$`) so it matches the whole value as in Lucene, and turns `case_insensitive: true` into a leading `(?i)`.

- The operators only Lucene has answer 400 `illegal_argument_exception` naming the operator: `~` (complement, only when the `COMPLEMENT` flag is set), `&` (intersection), `<n-m>` (numeric interval), `@` (any string), `#` (empty language), and `"..."` (quoted literal). Each is refused only when its Lucene syntax flag is on (`flags: "NONE"` makes `&` and `<` ordinary characters, which is also how Rust reads them).
- Constructs that mean something different in the two grammars are not translated: `^` and `$` are anchors for Rust and literal characters for Lucene, `(?i)` and other inline flags are groups for Rust and literal text for Lucene, and Rust's `[[:alpha:]]` classes or `&&` set intersection inside a class have no Lucene meaning.
- A pattern Rust's parser rejects (an unclosed group, a backreference, `{,n}`) answers 400 with Lance's message (`regex parse error: ...`).
- `max_determinized_states` and `rewrite` are accepted and ignored.

The `term` / `terms` / `wildcard` / `regexp` / `prefix` SQL push down compares the column as a whole, so on a `list<utf8>` column (multi-valued `keyword`) the predicate has no type to coerce to and Lance refuses the scan as invalid input, answered as 400 (`There isn't a common type to coerce List(Utf8) and Utf8 in LIKE expression` for `wildcard`, `could not convert to literal of type 'List(...)'` for `term`).

## Tied hits at the cut of a bounded full-text page

A bare full-text page returns `min(size, hits.total)` hits on one node and on many, but the set of rows tied in score at its cut can differ between two runs and between node layouts; every other shape's tie order is the whole table reader's. The bare full-text page is `lance_match` or a stock `match` on a `lance_text` field (or another Lance FTS shape, or a `bool` whose scoring clauses are such shapes with scalar `filter` / `must_not` clauses) with no `sort`, no aggregations and no `post_filter`.

- For every shape whose Lance scan is unbounded, the coordinator orders hits with equal scores or equal sort values by their Lance row address (fragment id, then offset), the doc id order of one reader over the whole table, so the page is the same on one node and on many and equals the page one Lucene reader over the whole table answers.
- For the bare full-text page each executor asks Lance for a score ordered top list over the whole table and keeps the top `from + size` rows of its own fragments, widening the list until it holds that many own rows or every match has been seen; the coordinator merges the per executor pages by score, then row address. The page is therefore full whenever enough rows match, and which of the rows tied at the cut it holds is decided inside Lance (Lance 12.0.0).
  - `TopKCollector.insert` in `rust/lance-index/src/scalar/inverted/wand.rs` replaces its k-th entry only on a strictly greater score, so within one index partition the first tied rows in posting order are kept.
  - The cross partition merge in `rust/lance-index/src/scalar/inverted/index/search.rs` consumes the partitions with `buffer_unordered` and applies the same strictly greater rule (`push_scored_partition_doc` in `search_candidates.rs`), so the tied rows that survive are those of the partitions that finished first.
- No ordering rule in the plugin can make that page identical to a Lucene collector over the whole table, which collects every match and keeps the lowest doc ids. The plugin orders whatever set Lance returned by row address.
- A page whose ties at the cut have to be stable needs an explicit sort (`"sort": [{"_score": "desc"}]` is enough): the scan is then unbounded and the tie order is the whole table reader's.
- The fix belongs in Lance (a deterministic tie break in `TopKCollector` and in the partition merge, for example by row id).

## Vector search

- `lance_knn` accepts only `Float32` element types. `int8`, `uint8`, `float16` vector columns are surfaced in the attach notes but excluded from the mapping until the Java SDK gains a matching `setKey` entry point.
- Nearest-neighbour scores are `boost / (1 + distance)`, not metric-normalised. Compare within a query, not across queries or engines.
- Nearest-neighbour queries scan once per Lance fragment. Many small fragments issue many native scans; compact with the Lance writer's compaction step to reduce the overhead.
- Filter clauses other than `match_all` / `term` / `terms` / `exists` / `range` / `bool` inside `lance_knn.filter` are rejected with 400 (no push-down to Lance).
- `lance_knn` combined with an outer `bool.filter` runs the outer clause as a post-filter (Lucene layer). Wrap it inside `lance_knn.filter` to push it into Lance.

## Tables above the Lucene document bound

- Each group of a node's fragments is one fragment request, so a request over such a table costs one executor run per group instead of one per node: the `plugins.lance.fragment_dispatch.max_concurrent` semaphore admits the node's groups four at a time (default) and queues the rest, the timeout applies to every group's request, and the coordinator holds one response per group until the merge.
- A full-text query runs its whole table scan once per group (the same scan the subset executor case repeats per node), and Lance's document set cannot represent a table of that size in one inverted index either; full-text search over such a table is not expected to work.
- `{index}/_stats` `docs.count` and `docs.deleted` count the fragments the shard reader holds. `GET /_plugins/_lance/stats` reports the table's rows (`indices.<index>.rows`) next to the reader's (`shard_reader_rows`) and `lucene_bound_exceeded`. Under a reader wrapper (the security plugin's DLS / FLS) both counts, `nested_docs`, `index_types` and `renamed_fields` are omitted from the index's entry, because they are read outside the wrapper.
- `GET /_doc/{id}` of a row outside the shard reader opens a reader over that row's fragment; when a reader wrapper is installed on the index (the security plugin's DLS / FLS, read off the node's `IndexService` whatever the wrapper returned for the caller) that reader cannot carry the filter and the GET fails with an `illegal_state_exception` instead of answering outside it. Rows inside the shard reader are filtered.
- A table with a single fragment above the bound cannot be read by any reader and is refused at attach (400).

## Shard model and concurrency

- Lance-backed indices are always single-shard. `POST /_plugins/_lance/attach` rejects any request carrying `number_of_shards` with 400. Fragment path fans out per fragment to every data node regardless of shard count or replica settings, so neither influences search parallelism; a replica copy of a Lance-backed index adds nothing to query throughput.
- Fragments are assigned round-robin by fragment id without regard to size, and a request fails as a whole when any one node fails. The fan-out covers every data node in cluster state, so the plugin has to be installed on all of them; a data node without the plugin fails the request with `ActionNotFoundTransportException`.
- On a node without a shard copy the executor creates a temporary `IndexService` per request through `IndicesService.withTempIndexService` (analyzer construction and mapping parse). It is not cached: OpenSearch offers no public way to keep an unregistered `IndexService` alive beyond that call, and a registered one is closed by the cluster state applier as soon as it sees the node holds no shard of the index.
  - Measured: 3.5 to 8 ms per request on the four column test fixture once the node has served one, about 100 ms for the very first request on a freshly started node, independent of row count.
- `PUT /{index}` with `index.plugins.lance.table` in settings is rejected with 400 pointing at `POST /_plugins/_lance/attach`. The engine can wire up without derivation via that path, but mapping ends up empty and every typed query fails; the reject prevents silent half-broken indices.
- Fragment path concurrency is capped by `plugins.lance.fragment_dispatch.max_concurrent` (default 4). Per-query heap (the sparse FTS and knn hit lists of 8 bytes per matching row, aggregation buffers) scales with concurrency rather than shard fan-out; without a cap, allocation can race the `lance_native` circuit breaker into `OutOfMemoryError` before the breaker fires. Requests over the limit block waiting for a permit.
- The coordinator half of a request (resolving the index, enumerating fragments, sending the per-node requests, merging the answers) runs on the plugin's `lance_coordinator` pool. When the pool is full the request fails with HTTP 429 and a `rejected_execution_exception` naming the pool, at its entry or at its merge; it is not run through the shard engine's reader instead.
  - `thread_pool.lance_coordinator.size` defaults to `max(1, allocated processors / 2)`; `thread_pool.lance_coordinator.queue_size` defaults to 10,000.
- A per-node fragment request is bounded by the request's `timeout` (else `search.default_search_timeout`, whose default is no timeout).
  - Without one, a request whose executor never answers (a node that hangs without leaving the cluster) stays open until the client gives up; the client closing its connection cancels the coordinator and executor tasks.
  - With one, a node that does not answer in time is cancelled and the response is partial (`timed_out: true`, `hits.total` with relation `gte`, aggregations reduced from the nodes that answered) or, under `allow_partial_search_results: false`, a 504.
  - The timeout is measured at the coordinator from the moment the per-node request is sent, so it includes the time the request waits for a `plugins.lance.fragment_dispatch.max_concurrent` permit on the executor. A cancelled executor stops at the next Lance batch boundary, not inside a batch.
  - That does not hold for the flat BM25 scan of a `lance_text` column without an inverted index ([mapping-overrides.md](mapping-overrides.md#type-lance_text)): Lance collects every row's tokens before it scores anything, so the first batch is the end of the scan and the cancelled executor runs it to the end. Measured over 20M rows without an index, a `match` with `timeout: 100ms` returned the partial answer (`timed_out: true`) in 108 ms and the executor kept about 7 cores busy for another 6 seconds, visible in `_tasks`. `search.default_search_timeout` behaves the same way. On this path a timeout bounds the client's wait and not the executor's CPU or native memory; the admission gate bounds the memory ([admission.md](admission.md#fts_flat)).
- When a reader wrapper is installed on the index (the security plugin's DLS / FLS wrapper), `hits.total.value` and `_count` are counted from the wrapped reader's live docs on every request shape: `match_all` in any spelling reads the liveDocs bitset, everything else collects the query's scorer under those liveDocs. The Lance metadata counts (`Dataset.countRows`, `Fragment.countRows`) and the count-only Lance scans that serve unwrapped indexes are not used, so a filtered user's count costs a pass over the matching rows instead of a metadata read.
  - Such an index renders its pages on the query round: every executor takes its own top `from + size` rows and the coordinator discards all but the page. The fetch round ([features.md](features.md#hit-shape)) has no search context to run the wrapper's decision in, so it is not used for a wrapped index; a cluster with the security plugin gets no fetch round for its Lance backed indexes.
- Full-text queries (`lance_match` and the other Lance FTS shapes) scan Lance without a fragment list on every node. Lance 12 turns a fragment list into a `_rowid` prefilter read over the listed fragments, so a node that executes a proper subset of the fragments (several data nodes) looks the whole table up from the inverted index and keeps the rows of its own fragments by the fragment id in `_rowaddr`; the lookup is repeated once per node but does not depend on the row count.
  - For shapes whose hits scan needs every match (aggregations, sort by a field, post_filter) that lookup is a probe whose row limit is `min(plugins.lance.fts.subset_probe_limit, max(plugins.lance.fts.subset_probe_min_rows, floor(rows the node covers * plugins.lance.fts.subset_probe_ratio)))`. The defaults are 1,000,000, 10,000 and 0.03; the limit is 200,000 on a 20M row table over 3 nodes.
  - When a query matches more rows than the limit, a node holding a proper subset discards the probe and repeats the scan with its fragment list, so that shape falls back to the prefilter read and its latency grows with the row count of the subset.
  - The exact count behind `track_total_hits: true` and `_count` is one count only scan with the node's fragment list on every node, so it pays the prefilter read once and never repeats the index lookup; the probe settings do not apply to it.
  - Removing the prefilter read itself needs a Lance-side change (a fragment-bitmap prefilter instead of a row id read).

## Primary key semantics

- `GET /<index>/_doc/<id>` requires the Lance table to carry `lance-schema:unenforced-primary-key` metadata on the PK column. Tables without a declared PK expose an empty `primary_key_field`; GET returns 404. `_search` still emits unique `_id` values synthesised as `<fragment>-<offset>`.
- Signed integer, UInt64, and Utf8 PKs are supported. Unsigned integer PKs narrower than 64 bits (UInt8 / UInt16 / UInt32) are not surfaced because OpenSearch has no matching unsigned mapping type below `unsigned_long`.

## Freshness

- Every read sees the table's current version on its next call after a Lance commit, whichever API it comes through. The fragment path (`_search`, `_count`) opens the latest manifest per request and the executors build a snapshot for it; the engine path (`GET /_doc/{id}`, `_mget`, `_stats`, a `_search` over a target that mixes a Lance backed index with another index) refreshes the shard's reader before every read and swaps it when the manifest moved. Each costs one manifest read per request; a pinned index (`index.plugins.lance.version`) opens nothing and never moves.
- The mapping follows the first request that observes a new table version. The coordinator of a `_search` or `_count` that read a version the mapping was not derived at asks the node holding the shard to run the freshness check at once, once per version; the scheduled check at `plugins.lance.namespace.poll_cadence` (default 10s) and `POST /_plugins/_lance/sync/{index}` remain for an index nobody queries. Until that check has applied the mapping, a column the table gained is absent from `GET /{index}/_mapping` and `_field_caps`, and the consumers that resolve a field through the mapping do not see it: sorts, aggregations, `fields` and `docvalue_fields`, stock full text clauses on it, and any query shape the planner leaves to the Lucene side. A `term`, `terms`, `range` or `exists` filter the planner runs as a Lance scan resolves the column from the Arrow schema of the version the request read, and the hits render it in `_source`, so those answer on the first request. The window for the rest is the duration of that one check (a manifest read and a mapping update), not a cadence.
- One node checks each index: the one holding its shard. After a node restart or a shard relocation the first check on the new node derives the mapping again even when the table did not move, one cadence after the shard starts or on the first request that reads the index, so an operator who wants the mapping caught up at once after a restart calls `POST /_plugins/_lance/sync/{index}`.
- `index.plugins.lance.uncovered_fragment_policy` (`wait` / `immediate`, default `immediate`) exists in settings but both values expose the new version at once. `wait` has no effect beyond one informational log line per index. Covering appended fragments with the table's indexes is the writer's job (pylance `ds.optimize.optimize_indices()`).

## Storage and credentials

- `storage_options` are stored in index settings (`index.plugins.lance.storage_options.<key>`). Keys the plugin classifies as credentials (any name containing `secret`, `password`, `token`, `key`, `authorization` or `credential`) are withheld from `GET /<index>/_settings`, `GET /<index>` and the cluster state API; `aws_region`, `aws_endpoint` and `allow_http` stay visible. The filter acts on the API output only: data nodes read the values from the cluster state as before, and a snapshot's index metadata carries them in clear because core writes the snapshot's metadata without the settings filter. Read access to a snapshot repository is therefore read access to the credentials, and the repository must be protected like them. Error messages and log lines also get credential shaped values replaced with `***` (the value of a key the plugin classifies as a credential, an AWS access key id, the `<AWSAccessKeyId>` element of an S3 error body, a `Bearer` or `Basic` authorization value, the `sig` parameter of an Azure SAS URL); this depends on the shape of the error body Lance and the object store return, so a new shape that carries a credential is a bug to report. Keystore / `SecureSetting` integration and the lance-namespace vended-credentials flow (`vend_credentials`, `expires_at_millis`) are not wired.
- The security plugin's audit log records the body of `POST /_plugins/_lance/attach` and `POST /_plugins/_lance/namespace` as it arrived, `storage_options` and `config` credentials included, when `plugins.security.audit.config.log_request_body` is on, which is its default, and a REST layer audit category that carries the body is enabled. The categories are the values of `plugins.security.audit.config.disabled_rest_categories`:
  - `AUTHENTICATED` records every authenticated request. It is disabled in the default audit configuration.
  - `FAILED_LOGIN` records a request whose OpenSearch credentials were wrong. It is enabled by default, so an attach sent with a wrong password and real storage credentials is recorded in full.
  - `GRANTED_PRIVILEGES` and `MISSING_PRIVILEGES` apply to routes the security plugin authorizes at the REST layer, which the plugin's routes are not. The record is written before authorization, so a request the plugin's transport action later refuses with 403 is recorded the same way. The plugin's redaction covers its own responses and logs and does not reach the audit log, which is written by the security plugin from the raw HTTP body (`AuditMessage.addRestRequestInfo`); the only masking there is for the security plugin's own account and user APIs. The records go to the `security-auditlog-*` indexes or the configured sink, so read on those indexes is read on the credentials. An operator who enables the audit log should set `plugins.security.audit.config.log_request_body: false`, or list `/_plugins/_lance/attach` and `/_plugins/_lance/namespace` under `plugins.security.audit.config.ignore_requests`, which drops the REST layer record of those calls; the transport layer record, which names the action and carries no body for the plugin's requests, stays.
- A namespace registration of type `rest`, `glue`, `iceberg`, `polaris` or `unity` makes the elected cluster manager connect to the endpoint in its `config` on every poll. `plugins.lance.allowed_catalog_endpoints` bounds the endpoints ([features.md](features.md#attach-and-namespace-surface)), and the host is checked as written, not resolved; `cluster:admin/lance/namespace/update` should be granted with that in mind.
- `storage_options` and the namespace `config` map accept at most 64 entries, keys of at most 256 bytes and values of at most 4 KiB (UTF 8 bytes); the bounds are fixed, not settings, and a map outside them returns 400 naming the count or the key and its length, never the value.
- An attach whose `storage_options` the object store refuses (S3 `InvalidAccessKeyId`, `SignatureDoesNotMatch`, `AccessDenied`, `ExpiredToken`, `InvalidToken`, and the GCS and Azure equivalents listed in [design/lance-error-mapping.md](design/lance-error-mapping.md)) answers 400 with the store's redacted error; a namespace whose credentials the store refuses is listed as `unavailable` with the same message. An attach of a URI whose bucket or container the store does not have (S3 `NoSuchBucket`, Azure `ContainerNotFound`, which is what a bucket name in the wrong case gets) answers 400 the same way. A search that fails because a session token expired after the attach stays a 500, because the request path does not classify store errors.
- Base-scoped options (`base_<url>.aws_access_key_id`) for nested Lance references are out of scope for now.
- The plugin has no read cache on local disk, and Lance's object store layer has none either. A table on S3, GCS or Azure is read from the store on every request, except for the index parts and columns that are already in memory (the Lance Session cache, the column store); a node restart empties those. "Serving an object store table from local NVMe" in [getting-started.md](getting-started.md#serving-an-object-store-table-from-local-nvme) gives the two operational ways of putting the table on local disk.
- Hive Metastore catalogs (Hive 2 / Hive 3) are not wired to the namespace endpoint; the dependency findings are in the section "Hive Metastore catalogs" below.
- The wired catalog clients (`glue`, `iceberg`, `polaris`, `unity`) are the 0.4.1 `lance-namespace-impls` artifacts, which build against lance-namespace 0.7.7 while the plugin bundles 0.11.1. The surface the plugin drives was verified by `javap` descriptor comparison and offline initialisation tests only, not against every catalog server version.
- Sub-directory tables of a directory namespace (`root/sub/table.lance`) are not surfaced: the directory poller lists top-level tables only. For the catalog types the poll walks nested namespaces down to `config.max_namespace_depth` levels (default 2).
- Namespace registrations live in cluster state and survive full cluster restarts. Every node's poll cycle reads the same set, so a multi-node cluster registers a path once.
- The Lance JNI namespace handle (`DirectoryNamespace`) has no synchronisation between `close` and the other native methods: `close` frees the Rust object at once and a call still running on another thread reads freed memory (a SIGSEGV, not an exception). The plugin guards every cached handle with a read/write lock so a release waits for the calls in flight; nothing outside the plugin's `LanceNamespaceService` should hold a raw handle.

## Hive Metastore catalogs

The `hive2` (`org.lance:lance-namespace-hive2:0.4.1`, Hive 2.3.9 thrift client) and `hive3` (`org.lance:lance-namespace-hive3:0.4.1`, Hive 3.1.3 `hive-standalone-metastore`) implementations of the Lance Namespace interface are not bundled.

The findings below come from three probes: resolving each artifact's dependency closure with `hive-exec` excluded; running the two clients against a `thrift://127.0.0.1:1` endpoint and (for `hive2`) against an in-process `libthrift` `TServer` answering `get_all_databases` / `get_all_tables` / `get_table`; and comparing class names across the OpenSearch 3.8.0 core classpath, the plugin's bundled jars and each candidate set.

- Neither client needs `hive-exec`. The metastore server side (`derby`, `datanucleus`, `javax.jdo`, `HikariCP`, `bonecp`, `hbase-client`, `tephra`, `hive-service`, `hive-llap-*`, `jetty`, `zookeeper`, `curator`) is never loaded by the client path and can stay out.
  - The classes both clients load on the connect, list and describe path come from `hive-metastore` (2.x) or `hive-standalone-metastore` (3.x), `hive-common` (`HiveConf`, `HiveStringUtils`), `hive-serde` (2.x, the single `serdeConstants` class), `hive-shims-common` (2.x, `Utils$JaasConfiguration`), `libthrift`, `libfb303`, `hadoop-common`, `hadoop-auth`, `hadoop-annotations`, `hadoop-mapreduce-client-core` (`HiveConf.initialize` references `JobConf`), `htrace-core4`, `commons-collections`, `commons-lang`.
  - Also loaded: `commons-configuration` (2.x) or `commons-configuration2` plus `woodstox-core` and `stax2-api` (3.x), `javax.servlet` (`Utils` in `hive-shims-common` references `javax.servlet.Filter`), and the `log4j` 1.x API, which `log4j-1.2-api` at the OpenSearch log4j version satisfies.
- The two types cannot ship together: `jarHell` rejects the pair, so only one Hive major version can be bundled per plugin build.
  - `hive-metastore` 2.3.9 and `hive-standalone-metastore` 3.1.3 both define `org.apache.hadoop.hive.metastore.**` (3672 identical class names).
  - `hive-common` 2.3.9 and 3.1.3 both define `org.apache.hadoop.hive.conf.**` and `org.apache.hadoop.hive.common.**` (150 names, plus 13 that `hive-standalone-metastore` 3.1.3 duplicates from `hive-common` 2.3.9).
  - Hive 3.1.3's `HiveConf` needs Hadoop 3.1.0 while Hive 2.3.9's needs Hadoop 2.8.5, so `hadoop-common`, `hadoop-auth`, `hadoop-annotations` and `hadoop-mapreduce-client-core` collide across the two versions (2944 names).
- Either type alone passes the class-name check against the core and plugin classpath (0 duplicates for `hive2` alone, 0 for `hive3` alone), at 18 MB (`hive2`, 18 jars) or 22 MB (`hive3`, 19 jars) of additional jars, against the 32 MB the wired catalog clients added together. `hive-metastore` alone is 8.2 MB, `hive-standalone-metastore` 11 MB, `hadoop-common` 4 to 4.3 MB.
- `thirdPartyAudit` is the remaining gate and was not run to green. Bundling a Hive metastore client means importing the audit lists of OpenSearch's `repository-hdfs` and `ingestion-hive` plugins, or shading the Hive and Hadoop closure with the Gradle shadow plugin so the audit sees one relocated jar.
  - A `jdeps` scan of the `hive2` set against the core, plugin and candidate jars leaves 532 unresolved class references (557 for `hive3`), spread over the metastore server side, YARN, HBase, Avro, DataNucleus, Jetty, ZooKeeper and Curator, Jackson 1.x, javax.mail and javax.jms. Every one of them would have to be enumerated under `ignoreMissingClasses` with a per-group justification.
  - `hadoop-common` carries `sun.misc.Unsafe` users (`FastByteComparisons$LexicographicalComparerHolder$UnsafeComparer`, `NativeIO`) that OpenSearch's own `repository-hdfs` and `ingestion-hive` plugins list under `ignoreViolations`.
- The version skew is the same as for the other 0.4.1 clients: the artifacts build against lance-namespace 0.7.7 while the plugin bundles 0.11.1. The offline connection test confirms the two clients load, initialise and reach the thrift transport (`TTransportException: Connection refused`) on this classpath without `NoClassDefFoundError`.
  - All 42 model getter and setter references and all 7 error-class constructors the `hive2` client uses exist in 0.11.1; the no-argument constructors of the nine response classes (`ListTablesResponse`, `DescribeTableResponse`, ...) are implicit default constructors in 0.11.1 and resolve at link time.
- The `HiveMetaStoreClient` connect loop blocks the calling thread for over ten minutes on an unreachable metastore with the default retry keys, so a registration would hold the poll thread for that long per cycle unless those keys are lowered.
  - The connect loop retries on transport failure for `hive.metastore.connect.retries` attempts spaced by `hive.metastore.client.connect.retry.delay`, and `RetryingMetaStoreClient` wraps that in its own `hive.metastore.failure.retries` loop; the ten minutes were measured in the probes above.
  - `HiveConf` also reads `hive-site.xml` from the classpath and the `HIVE_CONF_DIR` environment variable at construction time.

Shipping one of the two would take the following changes. The alternative that avoids the closure entirely is a thrift-only client compiled from `hive_metastore.thrift` against `libthrift`, which is how OpenSearch's `ingestion-hive` plugin talks to a metastore.

- Bundle exactly one Hive major version (the plugin would gain a `hive2` or `hive3` type, not both).
- Bring `hadoop-common` at the matching Hadoop minor, or verify that the shaded `hadoop-client-api` / `hadoop-client-runtime` pair at that version supplies `Configuration`, `UserGroupInformation` and `JobConf`.
- Replace `log4j` 1.x and `commons-logging` 1.1 with `log4j-1.2-api` and `commons-logging` at the OpenSearch versions.
- Add the `ignoreMissingClasses` and `ignoreViolations` lists above or relocate the closure with the shadow plugin.
- Add `PropertyPermission`, `javax.security.auth.AuthPermission` and `javax.security.auth.kerberos.ServicePermission` grants for `HiveConf` and `UserGroupInformation` (the set OpenSearch's `ingestion-hive` plugin declares).

## Mapping coverage gaps

- The geo family is not surfaced. See [mapping-overrides.md](mapping-overrides.md) for `type: ip` and `type: wildcard`, which are available through the `overrides` clause on the attach and namespace bodies.
- Nested fields (`List<Struct>` → `nested`) serve `nested` queries and the `nested` / `reverse_nested` aggregations (through the aggregators, never the scan) but not `inner_hits` (refused with 400 when a nested query carries one), and no Lance SQL pushdown for nested predicates (DataFusion has no `UNNEST` in a filter; the Lucene side filters). `list<utf8>` children and `List<Struct>` inside an element (nested in nested) are skipped with a note.
- FTS and knn on struct children are not derived: a Utf8 child always maps to `keyword` (never `lance_text`) and a `FixedSizeList` vector child is skipped with a note. A struct child type outside the scalar derivation (unsigned integers, binary, decimals) is skipped with a note while the parent `object` is still emitted; a struct with no supported descendants at all is skipped whole with one note instead of surfacing as an empty object. The same applies to nested element children.
- `Utf8` list, `Decimal`, and `FloatingPoint(HALF|DOUBLE)` columns are stored in the table but excluded from the mapping. The attach response notes them.
- Blob columns and `LargeBinary` beyond the basic `binary` mapping share the same status.
- Lindera and Jieba tokenizers are not bundled with lance-jni. Only ICU-based tokenization is available for CJK text through the Lance FTS index.

## Index lifecycle

- The engine is read-only. `_flush`, `_forcemerge`, `_settings` writes, `_close`, and `_open` on a Lance-backed index are either no-ops or unsupported; mutation happens on the Lance side.
- The plugin creates no Lance index. A column gets its inverted, scalar, zone map or vector index from the table's writer (pylance `create_scalar_index` / `create_index`, Ray, Spark, the Java SDK), and the freshness check picks the index up at its manifest commit.
- If an OpenSearch index already exists under the same name as a surfaced Lance table, the plugin logs one warning and leaves the table alone on every subsequent poll (`POST /_plugins/_lance/namespace/_poll` reports it under `skipped` with the reason). Rename, delete, or attach explicitly to resolve.

## Result cache

- Only a request whose body asks for no hits (`size: 0`, no `from`) is cached at the coordinator ([features.md](features.md#result-cache)). A request that renders hits, however small its page, fans out and runs its query on every repeat; what a repeat saves is the fetch of its rows, which the data nodes serve from the [fetch cache](features.md#fetch-cache) while the table stays at its version.
- The cache is per coordinating node. A client that spreads the same body over several coordinating nodes (a load balancer in front of the cluster) computes and stores the answer once per node, and `request_cache.hits` in `GET /_plugins/_lance/stats` is per node accordingly.
- A target that resolves to several indexes is not cached, whether every index is Lance backed or not; only a request against one Lance backed index is.
- The node settings a request runs under are not part of the key, so an answer computed before `plugins.lance.fragment_path.slices` or `plugins.lance.aggregation.pushdown` changed is served until the table moves on or `POST /{index}/_cache/clear?request=true` drops it. `_count` has no `request_cache` parameter and is cached whenever the cache is enabled.
- An index with a reader wrapper installed (the security plugin's document and field level security) is never cached, on every node, because the answer depends on the user. A cluster with the security plugin's DLS / FLS enabled therefore gets no result cache for its Lance backed indexes; `GET /_plugins/_lance/explain/{index}` reports `cacheable: false` with reason `dls` for such an index.

## Fetch cache

- The cache is per data node ([features.md](features.md#fetch-cache)). A node that joins or leaves moves fragments to other nodes under the round robin, and those nodes take the moved fragments' rows again on the next page.
- A cluster with the security plugin gets no fetch cache for its Lance backed indexes: the plugin wraps every request's reader, the admin's included, and a wrapped leaf neither reads nor writes the cache (`fetch_cache.skipped` in `GET /_plugins/_lance/stats` counts its rows).
- The entries of a table version are dropped when its snapshot closes, which the freshness check does on the node that holds the shard; on the other data nodes they stay until `plugins.lance.cache.max_snapshots` evicts the snapshot, the index is deleted, or the least recently used eviction reaches them. They cost heap, not correctness: no request keys on a retired version.
- A request served from the cache still runs its query on every data node; only the take of its rows is saved. `profile.lance` does not yet report the cells the cache served per request; the node wide `fetch_cache.hits` and `rows_served` counters do.

## Stats and monitoring APIs

`_cat/indices`, `_cat/shards`, `{index}/_stats`, `_nodes/stats/indices`, and `_cluster/stats` report a Lance-backed index as follows.

- `docs.count` and `docs.deleted` are the Lance row count and deletion count of the manifest version the shard currently serves (they advance on refresh, so a Lance write shows up after the next freshness check or an explicit `_refresh`). For a table above the Lucene document bound they count the fragments the shard reader holds, not the table: `GET /_plugins/_lance/stats` reports the table's rows as `indices.<index>.rows` next to `shard_reader_rows`.
- `_cluster/health` reports green for the single primary shard; it turns red only when the shard fails to open the table (unreachable path, missing credentials, dropped table), because there is no replica to fall back to.
- `store.size`, `pri.store.size`, and `store.size_in_bytes` are the size of the shard's Lucene directory, which holds only the bootstrap commit (a few hundred bytes), not the Lance data. OpenSearch computes the store size from the shard directory and offers no engine-level override. The manifest-recorded data file total is available internally as `DocsStats.totalSizeInBytes` (used by `_rollover` size conditions); data files written without a `file_size_bytes` manifest entry contribute zero to that total, and Lance index files (`Index.getSizeBytes()`) are not included anywhere.
- Segment fields (`segments.count`, `segments.memory`, the per-shard list in `_segments`) and the write-side groups `indexing`, `merges`, `flush`, `translog.operations`, `warmer`, and `recovery` are always 0 or empty. There are no Lucene segments and no OpenSearch-side writes; the values are not synthesised from Lance metadata. `refresh.total` also stays 0: Lance version advances swap the reader without going through the shard's refresh listeners, and `search.*` stays 0 because `_search` is answered by the fragment path, not the shard.
- `suggest.*`, `completion.*`, `fielddata.*`, `query_cache.*`, `request_cache.*`, `memory.total`, and the matching `_stats` cache groups stay 0 as well: the fragment path never reaches the shard-level caches or suggesters. The plugin's own result cache for `size: 0` requests is reported under `request_cache` in `GET /_plugins/_lance/stats`, not here. `get.*` is the one request counter that does move: `get.total` counts `GET /_doc/{id}` on a table with a declared primary key (the only request shape the shard engine serves itself).

## Reader memory profile

- Each Lance fragment leaf loads columns lazily. On the fragment path the leaf is a view over a cached table snapshot (see features.md, "Snapshot and column cache"): numeric, boolean, date, float, keyword and keyword array columns it reads for the whole fragment live off-heap in the node's column store and are shared across requests.
  - A keyword load interns the fragment's values in heap while the scan runs and releases that once the dictionary and ordinals are written off-heap.
  - Two keyword shapes are still built per request in heap and dropped when the request ends: the dictionary of a small full-text or vector hit set (the sparse hint path), and a keyword column read under a top-level filter that was pushed into the column scan.
- The shard engine's reader (`GET /_doc/{id}`, `_mget`, stats, and a `_search` over a mixed target) is a view over the same snapshot and reads columns from the same store. It stays open for the life of the shard at the version it last read (it refreshes before every read and swaps when the manifest moved), so it pins that snapshot: a shard that nobody reads keeps one dataset open per node that hosts it until the scheduled check moves it on, and a shard that falls through to a heap column load (store full) keeps that heap column until the next read or refresh at a newer version swaps the reader.
- `_id` and `_source` are not served from whole-column loads on either path. The fragment path fetches the rows behind the hits with a `_rowaddr IN (...)` take per leaf, projected to the columns the body renders (its `_source` filter, its `fields` and the primary key; see features.md, "Hit shape"): a `size:10` fetch with `_source: false` reads ten values of the key column, one without a `_source` element ten rows of every surfaced column, regardless of table size. The leaves of one executor are taken side by side, up to `plugins.lance.fragment_path.parallelism` at a time. Queries that never render hits (aggregations, `size=0` hit counts) only touch the columns they consult. The cells a take returns stay in the data node's fetch cache (features.md, "Fetch cache"), in heap, keyed on the table version, so a repeat of the page while the table stays at that version takes nothing; the cache is per node and bounded by `plugins.lance.fetch_cache.size` (1 percent of the heap by default), so a node that executes many fragments of a wide table keeps the most recent pages only. How many takes ran, how many rows they addressed, how many columns they projected and how long they took is reported per node under `fetch` in `GET /_plugins/_lance/stats` and per request under `profile.lance`, and the cache under `fetch_cache`.
- When the column store is full and nothing can be evicted (every held column is being read by a running request), the request loads the column into heap for itself, with the query's filter applied. The store's budget is `plugins.lance.cache.column_share` of `plugins.lance.native_memory.limit`; on a multi-node cluster every data node holds the columns of the fragments it executes, so a node that executes a subset of the fragments holds that subset only.
- A heap column load is charged to the node's request circuit breaker (`indices.breaker.request.limit`, label `lance_heap_column:<column>`) before its arrays are allocated and given back when the reader closes. A load the breaker refuses ends the request with HTTP 429 `circuit_breaking_exception` whose message names the column, the bytes it asked for and the limit; the node keeps running.
  - A numeric or boolean column costs 8 bytes per row of the fragments the node executes plus one presence bit per row; a keyword column costs 4 bytes per row plus its sorted dictionary.
  - The parent breaker samples real memory and does not see an allocation of several gigabytes before it fails, so without this charge a 1B row table whose columns overflow the store could exit the JVM with `OutOfMemoryError`.
  - `GET /_plugins/_lance/stats` reports the bytes currently charged as `column_store.heap_fallback_bytes` and the refusals as `column_store.heap_fallback_rejections`.
  - To clear repeated refusals raise `indices.breaker.request.limit`, raise `plugins.lance.cache.column_share` so the store keeps the column, or add data nodes so each executes fewer fragments. A shard engine reader that took a heap column keeps it charged until the next refresh swaps the reader out.
- An inverted index has to fit one shard of the Lance index cache as a single entry, or every full-text query reloads it from storage (about 2.9 s at 100M rows). `POST /_plugins/_lance/attach` logs a warning when a table's estimate is heavier than the share.
  - The entry is about 52 bytes per row per full-text column: about 4.8 GiB at 100M rows, about 48 GiB at 1B rows.
  - The share per shard is the capacity the plugin chose divided by the shard count (`GET /_plugins/_lance/stats`, `native_memory.index_cache_shard_share`); with the default settings on a 16 CPU node it is 8 GiB, so 100M rows fit and 1B rows are not expected to fit on one node under any setting (a share of 48 GiB needs a capacity of 8 times that on 16 CPUs).
  - Whether the 1B row table's inverted index is retained is to be confirmed on the perf1b table once its index is built.
- A native scan or index load over a table large enough for the node is refused with 429 `circuit_breaking_exception` (label `lance_admission`) by default when the gate's estimate does not fit the node's available physical memory (`MemAvailable` on Linux) minus `plugins.lance.admission.headroom`. A 429 on a table whose scan does not fit the node is the designed outcome, not a failure of the plugin.
  - Such a scan makes Lance allocate memory outside the JVM and outside every budget the plugin reads (an inverted index document set or the matching BTree pages that do not fit the index cache shard, the IVF partitions a nearest scan probes, the row addresses a filtered scan materialises, the read queue and decoded batches of every scan, the heap copy of a column the store could not hold), and a kernel OOM kill ends the node before any breaker sees the allocation.
  - What the gate estimates per path and what it does not, so an operator can read a refusal and an admitted kill alike:
    - `fts`: `rows × 52 bytes` for the document set (an upper estimate derived from a measured entry) plus the expected returned rows at 12 bytes, doubled. Not estimated: the posting buffers of the terms, the sort or aggregation columns the matched set costs downstream.
    - `scalar_index`: the matching share of the index (BTree pages, bitmaps held twice, a zone map whole) from its manifest size and the filter's selectivity. Not estimated: the selectivity of anything but an equality on a column whose index reports a distinct count (a BTree reports none; every other predicate is assumed to select one row in five), the pages other filters of the same request touch, an index whose column name the SQL does not spell as a bare identifier.
    - `filter_scan`: the matching rows at 256 bytes each, the batches in flight and the read queue. Not estimated: Lance's fragment read ahead (`fragment_readahead`), concurrency between requests (each request is judged against the same `MemAvailable` reading; two requests admitted at once can together exceed it). The take of data columns a `_source` page needs behind the addresses is judged on its own as `fetch_take`.
      - The per row constant is pinned to one measurement (a 10B row `term` at about one fifth selectivity exceeding 500 GB resident); the code accounts for 16 bytes per row and the rest is not attributed yet, so the estimate is 16 times what the code names and may over-refuse tables between 1B and 10B rows until the measurement round fits it.
    - `vector_index`: the index's manifest size scaled by `nprobes` over the partition count the table statistics report, loaded twice. Not estimated: the prefilter's row ids per partition, the scratch buffers of a residual or Rabit quantisation search, the uneven partition sizes of a skewed index (the probed share assumes partitions of equal size).
      - The whole index twice when the statistics report no partition count (the index statistics could not be read, or an index format that reports none), which then refuses any nearest scan over an index heavier than half the node's available memory whatever `nprobes` says.
    - `aggregate_scan`: per parallel scan the read queue (capped at 2 GiB) and the decoded batches over the rows the filter keeps. Not estimated: DataFusion's hash aggregate state inside Lance (the group keys and accumulators of one scan, which grow with the distinct groups of a high cardinality key), the second round of scans a `percentiles` takes, the memory a first run leaves that a second run adds to (the retained pool credits it only once nothing is in flight).
    - `column_load`: the request breaker judges the heap copy before it is allocated; the gate only records it.
    - `fetch_take`: the rows of one take chunk (at most 4096 hits per fragment) at the projected columns' widths plus the row address, doubled. Not estimated: the heap the decoded rows occupy until the page is rendered (bounded by `plugins.lance.fetch_cache.size` only for what the fetch cache keeps), the pages Lance reads around a scattered row, and the chunks a page over many fragments takes side by side on the fragment path's threads (each chunk is judged on its own against the same `MemAvailable` reading).
  - Every estimate at or below the index cache shard share is zero, so scans whose buffers are smaller than one shard of the cache the node dedicates to Lance are never refused; the shard share is 8 GiB on a 16 CPU node with the default settings.
  - The estimates are models, not measurements of the scan: an admitted request can still exceed the estimate and a refused shape may have run on a machine with more slack.
  - `plugins.lance.admission.bounded_shapes_gated` set to `false` restores the pass-through for bounded full text pages and judges a bounded filter page on its limit, which then pay the rebuild or the materialisation ungated on every query.
  - `plugins.lance.admission.enabled` set to `false` passes every kind but `fts_flat`: a full text scan over a column without an inverted index (a `type: lance_text` override) is refused with 400 while the gate is off, because nothing else bounds what that scan allocates ([admission.md](admission.md#fts_flat)).
- An admitted scan leaves `MemAvailable` lower than before it by the memory it cached and the pages the allocator kept (about 7 GB per node after the first unbounded scan over a 1B row table on a 128 GB node). The rebuilt document set itself is released when the scan completes: the process resident set returns to within a fraction of a gigabyte of its value before the scan on a 100M row table.
  - The admission gate credits this retained memory to the next decision on a scan of the same kind over the same index (`admission.retained_bytes` and `admission.retained_scope`, see [admission.md](admission.md#retained-memory)), which is what lets a repeat of an admitted shape through while a different shape is judged on the available memory alone. The credit is capped by what the process actually kept, so a node whose available memory falls for another reason still refuses.
  - Every repeat pays the transient rebuild again, so a node has to hold the estimate above `plugins.lance.admission.headroom` once more each time. On a 128 GB node with the default 31 GB heap and 40 percent native limit, the caches filling to their budgets leaves about 35 GB available, below the 1B row estimate, and no unbounded full text scan over such a table is admitted from then on.
  - Lowering `plugins.lance.native_memory.limit` or the heap on that node, or reading the table from more nodes, is what makes room; the gate cannot.
- Snapshots retired by the freshness check (table advanced, tag moved) are closed only on the node holding the shard, where the check runs. Other nodes keep the previous version's snapshot until `plugins.lance.cache.max_snapshots` evicts it or the index is deleted; requests on those nodes already key on the new version, so the leftover costs one open dataset and its columns, not stale results.

## Version pinning

- `"version": N` on `POST /_plugins/_lance/attach` pins a Lance-backed index to a specific manifest version for readonly snapshots. Branch checkout is not exposed by the Lance Java SDK, so a Lance branch cannot be attached from OpenSearch. Tag checkout is supported through the attach body's `"tag": "name"` clause; the freshness check re-resolves the tag on every cycle, so the index tracks a moving tag.

## Snapshot and restore

- `_snapshot` of a Lance-backed index stores the index metadata (settings including `index.plugins.lance.table`, `index.plugins.lance.version`, `index.plugins.lance.storage_options.*`, and the mapping) plus the shard's empty Lucene commit: one `segments_N` file of about 200 bytes. Rows and the Lance-side FTS / vector indexes stay in the Lance table and are not copied, so a snapshot is not a backup of the data. Back up the table with the storage layer's own tooling.
- Restore re-creates the index with the same settings and mapping. If the table is reachable at `index.plugins.lance.table`, the shard opens and `_search`, `_count`, GET and `_stats` serve the table as it is at restore time. An index without `index.plugins.lance.version` reads the latest manifest version, so rows appended or deleted after the snapshot are visible; a pinned index keeps its pin.
- If the table is not reachable, the engine fails to open (`Dataset at path ... was not found`) and every allocation attempt up to `index.allocation.max_retries` reports that error in `_cluster/allocation/explain`. The index stays red with the primary `UNASSIGNED` / `ALLOCATION_FAILED`. `_search` and `_count` both return 400 with the Lance not-found message because the fragment path they run on cannot open the table either.
  - Once the retries are exhausted the restore itself is marked failed, so `POST /_cluster/reroute?retry_failed=true` does not help even after the table is back: OpenSearch refuses to allocate a primary whose restore has failed. Delete the index and restore it again.
- The same engine failure outside a restore (for example `POST /{index}/_open` while the table is unreachable) behaves differently after the table is back: `POST /_cluster/reroute?retry_failed=true` starts the shard, because each failed attempt releases the shard's store and shard lock before the next one.

## Not yet implemented (RFC future work)

Items on the roadmap that no version of the plugin ships today.

- Analytics route via `sandbox/plugins/analytics-backend-datafusion`: not implemented. Every query takes the reader route.
  - The reader route reaches Lance's DataFusion-backed columnar aggregation for the shapes the [Aggregation pushdown](aggregations.md) covers, and Lance's scalar index resolver consults the Zone Map, BTree and Bitmap indexes whenever the scan carries a filter.
  - What the analytics route adds is a DataFusion runtime shared across plugins, the PPL and SQL entry points, and aggregation trees richer than the single `AggregateRel` root Lance accepts inside a scan; it is not the only path to SIMD aggregation or Zone Map pruning.
- PPL / SQL integration (lives in `opensearch-project/sql`): not implemented.
- OpenSearch analyzers on a Lance column (the RFC's second text mode): not implemented. Full text queries run through the tokenizer of the table's inverted index; stemming, stop words and language handling are the writer's choice at index creation (Lance's tokenizer options).
- Native ingestion via `_bulk` / `_doc` (RFC future work item 1): not implemented.
- Lucene custom index type stored in `_indices/{uuid}/` (RFC future work item 2): not implemented.
