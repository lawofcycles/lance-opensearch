- Every plugin internal message that travels between nodes now opens with a wire format version marker, the way `FragmentPlan` and `LanceExplainResponse` already did: the fragment request and response of the fan out (`LanceFragmentQueryRequest`, `LanceFragmentQueryResponse`), the per node stats request and the stats it returns (`LanceStatsNodeRequest`, `LanceNodeStats`), the per node `node_local` build request and response (`LanceBuildIndexesNodeRequest`, `LanceBuildIndexesNodeResponse`), the sync request and response the shard's node answers (`LanceIndexSyncRequest`, `LanceIndexSyncResponse`), and the poll, register and unregister and attach requests and responses the cluster manager answers (`LanceNamespacePollRequest`, `LanceNamespacePollResponse`, `LanceNamespaceUpdateRequest`, `LanceNamespaceUpdateResponse`, `LanceAttachRequest`, `LanceAttachResponse`). Each class carries a `WIRE_VERSION` constant (`1`, or `2` for `LanceExplainResponse` after D-6e retired the shard path fallback route and made the plan texts and traits optional for the unsupported route), written through the shared `WireVersion` helper as the first field after the fields its OpenSearch base class writes and read first. A node of another plugin version refuses the stream with `<Class> wire version [m] does not match this node's [n]: every node must run the same plugin version` before it reads a field, where a request between two plugin versions previously failed as a generic stream corruption wherever the layouts first diverged. Nothing negotiates between versions; the marker detects a mismatch and the request fails. `docs/query-plan.md` and `docs/architecture.md` describe the policy and how the number is bumped.
