- `docs/getting-started.md` follows the current API. The query walkthrough leads with the stock OpenSearch syntax (`match`, `match_phrase`, `multi_match`, `bool`) on `lance_text` fields, states what the stock form hands to Lance and what it drops (`operator`, `minimum_should_match`, phrase order, `slop`; `fuzziness` answers 400), and shows `lance_match` / `lance_match_phrase` / `lance_multi_match` / `lance_fts_bool` / `lance_fts_boost` as the explicit form under each stock example, with the `bool` prefilter that only the `lance_*` form plans as one Lance scan. The sample table scripts pass `with_position=True` for `body`, which pylance defaults to `False` and `lance_match_phrase` needs. A new subsection introduces `GET /{index}/_lance/explain` with the two answers the walkthrough's queries produce (`LUCENE_TOPK` with `unplanned: query type [match]` and `PUSHED_SCAN` with `filter_sql`) and how to read `route`, `logical`, `physical` (with the trait and cost terms on every operator line), `fragment_plan`, `unplanned`, `refinements_possible` and `traits`, pointing at `docs/query-plan.md` for the reference. The aggregation section describes where a tree runs (inside the Lance scan, through the aggregators, or refused with 400 for `global`, `top_hits`, `rare_terms`, `significant_terms`, `significant_text`), the fitted cost model that chooses between the pushed scan and `LuceneAggregateExec` with `lance.aggregation.pushdown` and `pushdown_max_groups` as cost inputs, and the four data node refinements (`security_wrapper`, `sort_field_type`, `aggregate_resolution`, `column_store_warm`) with the `plan` block of `GET /_lance/stats` that counts them. The mapping type list names `lance_vector` (what `_mapping` prints) and the troubleshooting section gains the stock `match` / `match_phrase` semantics, the missing positions error and the explain endpoint.
