- `GET /<index>/_lance/explain` answers what the coordinator would execute for the body. The endpoint plans through the same entry point the coordinator uses, with the same query rewrite, the same planner model and the same cost inputs (the cluster's data node count, the storage kind of the table URI and the parallelism settings), so it accepts every envelope the runtime accepts (`from`, `post_filter`, `_source`, a page next to aggregations, a query outside the translator's vocabulary, an empty body) and its only refusal is the one the runtime shares, a filtered `lance_knn` whose filter has no Lance SQL form. The response gains `route` (`fragment`, or `shard_path` with the `reasons` the planner names for a body only the shard path serves, whose physical plan is now shown instead of a 400), `fragment_plan` (the per node plan the coordinator ships: `kind`, `filter_sql`, `lance_clause`, the pushed `top_k` orderings and fetch, or the pushed `aggregate` summary), `unplanned` (the request element that kept the envelope on the Lucene side, with the translator's message) and `refinements_possible` (the node local downgrades a data node could still apply, `security_wrapper` and `sort_field_type`, predicted from the mapping and the plan); `physical` renders the coordinator's `MergeExec(FanOutExec(per node plan))` tree. The coordinator now costs its plan with the cluster's inputs as well, so a keyword `terms` over a billion rows on an object store plans as the Lucene aggregators on a multi node cluster where a single local node keeps the pushed scan; `docs/architecture.md` names the physical operator of every convention and what executes it.
