- A cluster can run the current and the previous plugin version at once while its nodes are upgraded one at a time. Every plugin internal message that travels between nodes keeps its version marker and now lays its fields out so both versions read it: the fields of version 1 inline, and the fields each later version added as a length prefixed block behind a flag (`WireVersion.writeBlock`), so a node of the previous version steps over the blocks it does not know and a node of the current version substitutes a fallback for the blocks an older writer never sent. The writer flags a block critical when ignoring it would change the answer, and a node of the previous version refuses such a message by name (`FragmentPlan wire version [3] adds fields in version [3] that this node's [2] cannot ignore: upgrade this node before sending it this message`) instead of answering wrongly. `FragmentPlan` carries its excluded fragment ids (version 2, optional) and its Substrait filter bytes (version 3, critical while a filter is set) as blocks, `LanceNodeStats` its pruned fragment counter (version 2, optional), and `LanceExplainResponse` decodes the version 1 stream of the retired shard path route as an unsupported answer. Nothing is removed from or retyped in a layout that shipped. `docs/design/wire-format-compat.md` holds the rules, the version history of every message and the compatibility matrix; `docs/query-plan.md`, `docs/architecture.md`, `docs/features.md` and `README.md` no longer state that every node must run the same plugin version.
