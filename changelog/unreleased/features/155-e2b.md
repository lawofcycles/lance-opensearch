- A data node answers a pushed aggregation from its column store when that is predicted cheaper than scanning an object store again. The coordinator ships, next to a pushed aggregate, the cost the model predicted for the scan, the cost it predicts for the Lucene aggregators when every column they read is already resident in the node's off heap column store (the same inputs over local storage, so no object store term), and the names of those columns. The fragment executor's refinement gains a fourth, cost based reason, `column_store_warm`: when the node's store holds every one of those columns for every fragment of the request and the resident Lucene cost is below the pushed cost, the aggregators run over the store instead of the Lance scan reading the object store. Over a local table the resident cost equals the cost the planner already compared, so the reason never fires there; over an object store table it fires once a Lucene side request (an aggregation the planner does not push, or a run with `lance.aggregation.pushdown: false`) has loaded the columns, because nothing warms the column store at attach (`lance.attach.warm_indexes` warms the Lance index cache). Below the fitted model's million rows the shipped costs are zero and the plan executes as before. `plan.refinements` in `GET /_lance/stats` gains the `column_store_warm` counter. (#155)
